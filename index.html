Toast

吐司 / 轻提示

自动消失，不打断任何操作

浮在界面上层的一小块短提示，出现两到三秒后自己消失。不抢焦点，不需要用户回应，背后的页面照样能点。最常见的用法是给刚刚完成的动作一句确认：「已保存」「已复制」。

容易混淆

和 Snackbar 的区别是「有没有动作」：Toast 只是一句话；Snackbar 专门为「撤销」这类单按钮设计，更宽、停留更久，通常贴在底部横跨。和 Notification 的区别是「要不要读」：Toast 一行字扫过就够，Notification 有标题和正文，等你处理。

SCREEN CORNER

Snackbar

底部横条 / 可撤销提示

底部一条，带一个操作按钮

从屏幕底部横着推出来的一条窄条，除掉一句话，右侧通常固定放一个操作，比如「撤销」。停留时间比 Toast 长（四到十秒），因为它要留给用户反应和点按钮的时间。是 Material Design 里专门为「我刚做了件可能后悔的事」准备的。

容易混淆

Snackbar 与 Toast 的关键差别不是位置，是「可操作性」：Snackbar 提供的是一个补救动作，点「撤销」就回滚；Toast 点不了。Snackbar 与 Banner 的差别是「在不在文档流里」：Snackbar 浮在底部盖住内容，Banner 在页面顶部把内容往下推。

Inline alert

内联提示 / 行内警告

长在内容里，不会浮起来

嵌在页面内容流中的一个色块，带图标和说明文字。它就待在自己该在的位置：表单出错时出现在出错字段旁边，说明性提示放在相关段落下。因为占据文档流的位置，它不会挡住任何东西，也不会自己消失 —— 只有当条件解除时才该移除。

容易混淆

和 Toast 的差别是「归属」：Toast 属于整个应用，浮在最上层；Inline alert 属于它所在的那块内容，滚走了就看不到。和 Banner 的差别是「范围」：Banner 是全局的、横跨整个视口；Inline alert 只在某个局部生效，可能一屏里有三个。

IN FLOW

Banner

横幅 / 全局公告

横跨整页顶部，常驻到被关掉

页面最顶端一条贯穿全宽的横条，用来讲一件影响所有人的事：服务维护、账单异常、试用快到期、Cookie 同意。它把页面内容整体往下推，而不是盖住内容。通常一直存在，直到用户主动关闭或者状态改变。

容易混淆

和 Inline alert 的差别是「作用域」：Banner 属于整个应用或整个页面，只能有一条；Inline alert 属于某个模块，可以同时存在多条。和 Snackbar 的差别是「是否占位」：Banner 占空间、会推动布局，Snackbar 悬浮覆盖在内容之上。

Notification

通知卡片

堆在角落里，等你有空读

从屏幕一角（通常是右上）滑入的卡片，比 Toast 大得多：有图标、标题、一行描述、可选的操作按钮。可以堆叠好几条，不会几秒就消失，需要用户关掉或者点进去。适合「值得知道，但不急着处理」的事件 —— 收到新消息、后台任务跑完了、有人提及了你。

容易混淆

和 Toast 的差别是「分量」：Toast 是一句扫一眼就过的话，Notification 是一张带标题和正文的卡片，能容纳决策。和 Modal 的差别是「阻不阻断」：Notification 不挡操作，Modal 要求你先处理它。系统级的推送通知（iOS / Android 通知中心）是另一回事，那个在应用之外。

CORNER STACK

Badge

徽标 / 角标

贴在图标上的数字或圆点

附着在图标、头像、标签右上角的一个小标记：一个数字表示未读数量，一个圆点表示「有更新」。它不是临时的 —— 只要状态还在，它就一直亮着，会随着状态消失而消失。所以它是状态的一部分，而不是一次事件提示。

容易混淆

和 Toast 的差别是「持续性」：Toast 是一次性的消息，看完就走；Badge 是持续存在的状态标记，用来告诉你「这里还有东西」。和 Tooltip 无关，但常一起出现 —— Badge 吸引注意，Tooltip 解释含义。数字超过 99 通常显示 99+，不要让它撑破布局。

Skeleton

骨架屏

用灰块先把布局占住

在内容到达之前，用灰色方块按真实布局的形状铺出来，带一点微弱的流动光。它的价值不在「转圈告诉你在加载」，而在「提前把位置占好」—— 内容是原地长出来的，页面不会在数据到达的瞬间整体跳一下。用在结构已知、只是数据没到的场合。

容易混淆

和 Spinner 的差别是「知不知道长什么样」：Spinner 只知道「在等」，Skeleton 知道要等出来的是列表还是卡片，所以能画出形状。经验规则：首屏内容用 Skeleton，局部小操作（按钮提交、下拉刷新）用 Spinner。别把 Skeleton 做得比真实内容更漂亮，否则加载完成反而是个失望。

库里叫

  • Ant Design：Skeleton
  • shadcn：Skeleton
无障碍
容器标 aria-busy="true"，并对读屏隐藏灰块本身；prefers-reduced-motion 下停掉流光。
何时用
首屏或列表第一次加载，且能预判内容的形状。
PLACEHOLDER

Spinner

加载指示器 / 转圈

我不知道还要多久

一个不停旋转的圆环，表示「正在进行，进度未知」。它不占具体位置，可以塞进按钮里、表格单元格里、页面正中。它的潜台词是「很快」，所以只适合一两秒内结束的等待 —— 超过几秒，用户会开始怀疑是不是卡死了。

容易混淆

和 Progress 的差别是「有没有可测量的进度」：能算出百分比（上传、安装）就用 Progress，算不出来（等接口返回）才用 Spinner。和 Skeleton 的差别是「是否保留布局」：Spinner 会让内容区域塌成一个小圆，Skeleton 让布局原地不动。等待超过 5 秒，最好在 Spinner 下面补一句「正在加载 128 条记录…」，让人知道它没死。

INLINE

Progress

进度条

能算出百分比，就别让用户猜

一条填充的横条（或圆环），表示已经完成了多少。分两种：确定型（有真实百分比，跟着任务推进）和不确定型（来回反复，本质是横着放的 Spinner）。文件上传、批量导入、安装、多步表单里都该用它，因为知道「还剩多少」能显著降低等待的焦虑。

容易混淆

和 Spinner 的差别只在「进度是否可知」，但用户体感差别很大：进度条会让人愿意等更久。别做假的进度条 —— 那种每次走到 90% 就卡住的，比没有进度更让人恼火。不确定型的 Progress 和 Spinner 功能重复，二选一就行，不要同时出现。

DETERMINATE

Empty state

空状态

没有数据时，告诉人下一步做什么

当列表、搜索结果、收件箱里什么都没有时，占据那块区域的说明：一张小插图、一句话解释为什么空、一个明确的按钮。空白屏幕是最糟的界面，因为它让人分不清「加载失败」「我没权限」还是「这里本来就没有东西」。空状态的任务是把这句话说清楚，并递出一个动作。

容易混淆

和 Skeleton 的差别是「会不会有东西」：Skeleton 是「还没来」，Empty state 是「确实没有」。这两种状态必须严格分开 —— 把加载中的空列表渲染成「暂无数据」，是新手最常犯的错误之一。另外要区分「第一次使用」和「筛选后无结果」，前者该鼓励创建，后者该提供「清除筛选」。

库里叫

  • 多数库无统一组件，按项目自建
无障碍
标题用真实标题层级，插图 aria-hidden="true"；说明文字要在 DOM 里而不是图里。
何时用
任何「查无内容」的容器，包括搜索结果和筛选结果。

Modal

模态框 / 弹窗

居中浮起，后面的页面暂时不能用

一层半透明遮罩盖住页面，中间浮出一个对话框。它是一个「次级任务」的容器：编辑一条记录、选一个文件、填一段说明。打开期间焦点被锁在框内，Tab 不会跑出去，Esc 或点遮罩可以关掉。关掉之后，焦点应该回到当初打开它的那个按钮上。

容易混淆

和 Alert dialog 的差别是「能不能随便关」：Modal 是常规任务，用户随时可以反悔退出；Alert dialog 是「必须先回答」，点外面和按 Esc 都不该关掉。和 Drawer 的差别是「内容量」：Modal 适合一屏能看完的表单，内容长、需要滚动就换 Drawer。少用 Modal —— 它是打断，用多了用户会烦。

Alert dialog

警告对话框

必须先回答，不能点外面溜走

一种特殊的 Modal，唯一目的是让用户对一件有后果的事做明确选择：真的要删除吗、要放弃未保存的修改吗、要覆盖这个文件吗。它刻意不提供「随便关掉」的出口 —— 点遮罩没用，Esc 也不该关，必须点「取消」或「确认」。这是把「确认」变成无法回避的一步。

容易混淆

Drawer

抽屉

从侧边滑出，装得下长内容

从屏幕侧边（多数在右边）滑进来的一块面板，通常是满高的。它和 Modal 做同样的事 —— 承载一个次级任务 —— 但能装下更多东西：一长串设置项、一条记录的完整详情、一个筛选面板。宽度可比 Modal 大，内容超出就自己滚动，而且滑出的动作本身就在告诉用户「这是从旁边推过来的，不是替换了当前页面」。

容易混淆

和 Modal 的差别是「体量」：内容短、要聚焦就用 Modal；内容长、要滚动就用 Drawer。和 Bottom sheet 的差别是「方向与设备」：Drawer 通常从侧边来，桌面端常见；Bottom sheet 从底边来，移动端常见。还有一点容易漏：Drawer 打开时背景依然可见，但同样要锁焦点。

FROM BOTTOM

Action sheet

动作面板 / 操作表

底部一列按钮，最后一定有取消

iOS 的经典形态：从底部升起一组大按钮，每个代表一个动作，最后单独隔开放一个「取消」。它不承载内容，只承载选择。触发场景往往是长按或点「⋯」：分享到哪儿、用哪个应用打开、要编辑还是要删除。危险动作（删除）会被标成红色，并和普通动作分开。

容易混淆

和 Bottom sheet 的差别是「有没有别的可能」：Action sheet 的答案注定在这一列按钮里，所以「取消」必须存在；Bottom sheet 是容器，里面放什么都行。和 Dropdown menu 的差别是「设备与位置」：同样的动作列表，桌面端用下拉菜单贴着按钮，手机端用动作面板从底部升起，因为拇指在下面。

Lightbox

灯箱 / 图片查看器

黑底全屏，只为看图

点开图片后铺满整个视口的浮层，背景压到接近纯黑，图片居中放大，两侧可切换上一张下一张，角上有关闭。它把周围一切无关的东西都去掉，因为此时用户唯一想做的就是看清这张图。常见的配套是缩略图条、「3 / 12」这样的位置提示，以及左右方向键。

Tooltip

工具提示

悬停一下，给个纯文字解释

鼠标停在一个元素上（或键盘 Tab 到它）之后，紧挨着弹出的一小块深色标签，通常只有一个词或一句话。它的职责是补充「这个东西是什么」—— 一个只有图标的按钮、一个被截断的文件名、一个术语。里面不能放按钮，不能放链接，因为鼠标一移过去它就消失了。

Dropdown menu

下拉菜单

点按钮，展开一列动作

点击一个按钮（通常是「⋯」或「操作」）后，在其下方展开的一列命令：编辑、复制、导出、删除。可以有图标、右侧快捷键提示、分隔线和分组标题。打开后方向键上下移动，回车执行，Esc 关闭。它回答的是「对这一个对象，我能做哪些事」。

容易混淆

和 Context menu 的差别只在「触发方式」：同样的菜单，左键点按钮就锚在按钮下，右键就锚在鼠标位置。和 Popover 的差别是「内容的同质性」：菜单里每一行都应该是同一种东西（一个可执行的动作），塞进勾选框或表单就已经不是菜单了。和 Select 的差别是「是否改变表单的值」：菜单里的动作立刻执行，Select 只是选一个值。

右键菜单 / 上下文菜单

右键，在鼠标那里弹出来

新手引导 / 分步导览

一步一步，带你看完整条流程

Select

下拉选择

从固定的一组选项里选一个

点开、列出全部选项、选一个、收起。选项是有限的、已知的，而且通常不多 —— 国家、时区、货币、语言。浏览器有原生实现，键盘、读屏、移动端滚轮全都免费。

Radio group

单选组

所有选项都摆出来，只能选一个

一组圆点，每个旁边一个标签，永远只有一个被选中。选项全部可见这一点很关键 —— 用户能一眼比较完所有可能性，不用先点开来找。适合互斥且需要对比的少量选项：套餐、配送方式、发票类型。

开关

拨一下，立刻生效

一个滑块，要么开要么关。关键在于「立刻生效」—— 拨完的那一刻设置就变了，不需要找保存按钮。所以它出现在设置页、通知偏好、功能开关里，而不是出现在需要点提交的表单里。

LEAVE GUARD

Disabled / Readonly

禁用 / 只读

三种「不能改」，行为完全不同

disabled：不可聚焦、不可点击、值不会随表单提交。readonly：能聚焦、能选中复制、值会提交，只是不能改。aria-disabled：视觉上像禁用，但仍然可聚焦、仍会提交，只是告诉读屏「现在不可用」。

容易混淆

最危险的错误是用 disabled 表达「暂时不能改」：值会被静默丢掉，提交时后端收到的是空。另一个常见错误是把「未填完所以按钮变灰」做成 disabled —— 用户点不了也不知道为什么。更好的做法是让按钮可点，点了再告诉他缺哪一栏。用 readonly 则表示「这个值是有意义的，只是不允许你改」，比如自动生成的订单号。

先当成功，失败再撤回
